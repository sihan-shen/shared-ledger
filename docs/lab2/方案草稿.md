# 实验二前端技术方案（草案）

> 状态：草案，仅本机保存；未 `git add`、未提交、未打包。
> 日期：2026-10-29（本地组件化方案更新）
> 项目：多人共享记账系统（实验一需求基线：REQ-001～REQ-041）
> 用途：锁定实验二 UI 设计与实验三实现所使用的前端技术栈，避免设计稿与代码组件对不上。
> 当前实施：`ui-prototype/` 已建立 React + shadcn/ui 本地原型，沿用 SDS 青绿 tokens。完整业务系统与全部 17 屏仍未完成；本文件中的后端、API 和完整应用选型属于后续规划。

## 1. 决策摘要

采用 **React 单栈 + shadcn/ui + SDS 青绿视觉规范 + 双壳**。每个页面保留一个主壳。

| 项 | 决策 |
| --- | --- |
| 框架 | React 19 + TypeScript + Vite |
| 路由 | React Router 7 |
| 服务端状态 | TanStack Query 5 |
| 客户端状态 | Zustand 5 |
| UI 基础 | shadcn/ui（Radix）+ Tailwind CSS 4 + CVA；基础件源码放本地，视觉映射到既有 SDS tokens |
| 表单 | React Hook Form + Zod |
| 表格/图表 | TanStack Table 8；ECharts |
| API 类型 | FastAPI `/openapi.json` → openapi-typescript + openapi-fetch |
| 设计方式 | 本地 React 交互原型 + 组件展示页；SDS + 青绿 CSS tokens；Figma 现有稿保留作历史参考 |
| 布局 | 一个 Vite 应用，两个 shell：`MobileShell` 与 `AdminShell` |
| 页面归属 | 一个页面只属于一个主壳，另一个宽度做响应式检查，不做同页双实现 |

**核心原则：**

1. 高频手机操作（登录、账本、记一笔、账目、审核、还款）用 `MobileShell`，移动优先。
2. 数据密集型管理操作（成员、预算、统计、日志、归档、维护端）用 `AdminShell`，桌面优先。
3. 两端共享 SDS tokens、API client、登录态、权限判断和金额/状态文案，也共享 Button/Input/Dialog 等基础件。
4. 用户端在 1440 宽下是居中的 720px 列；管理端在手机宽度做单列降级。

**兜底方案：** 如果实验三时间不足，**不要退回 Vue**；缩减管理端页面、延迟非核心功能，保留 React + SDS 单栈。

## 3. 为什么是 React + SDS

| 维度 | 结论 |
| --- | --- |
| 与 SDS 对齐 | SDS 是 Figma 官方设计系统，官方代码示例是 React + Code Connect；设计与实现可共用组件语义、变量和命名 |
| 单栈一致性 | 不再维护 Vue + Element Plus + Vant 两套视觉/表单/主题；用一套 SDS 风格 primitives |
| 课程允许 | 实验二只要求 UI 设计与建模；实验三实现可用主流前端栈；React 生态成熟 |
| 不引入 SSR | 项目是本地/局域网 SPA，FastAPI 提供 API；Vite 静态构建符合 REQ-038 |
| 不用 Next.js | 没有 SEO/SSR 需求；避免 Node 服务端运行时和额外部署复杂度 |

**SDS 不是 npm 组件包。** 官方 `figma/sds` 是设计系统 + React 示例 + Code Connect，不是可直接 `npm i` 的稳定组件库；实现用 Radix + Tailwind 本地写 SDS 风格组件，SDS 只作为设计与代码参考。

## 4. 总体架构

```text
浏览器（360 / 390 / 768 / 1440）
        │
        ├── /app/*      MobileShell
        │                登录、账本、记一笔、账目、审核、结算
        │
        └── /admin/*    AdminShell
                         成员、邀请、更正处理、预算、统计、日志、设置、维护端
        │
        └── 共享层
             ├─ router（route handle.shell 决定 shell）
             ├─ providers（QueryClient、Auth、Toast）
             ├─ api（openapi-typescript 类型 + openapi-fetch client）

             ├─ styles/tokens.css（SDS + 青绿）
```

### 4.2 边界规则

- `routes/mobile` 只使用 `MobileShell` 与移动优先组件；`routes/admin` 只使用 `AdminShell`。
- 业务组件不允许直接写死 hex/px；必须用 `tokens.css` / Tailwind token。
- 一个页面只做一个主壳；另一个宽度只做响应式检查，不做同页双实现。
- 路由级 `lazy` + `Suspense`，移动端不加载管理端表格/图表代码。
- 所有金额以整数分传输和计算，展示用 `Intl.NumberFormat`；禁止浮点金额。

## 7. 设计系统：SDS + 青绿

### 7.1 视觉规则

- **颜色**：品牌青绿 `#0F766E` / `#115E59` / `#14B8A6` / `#F0FDFA`；中性色用 SDS 灰阶；状态色 pending/success/danger/info。
- **形**：8px 圆角、1px 边框、无卡片阴影；靠边框和留白分层。
- **字**：Inter；中文 fallback `Noto Sans SC`；正文 16px，辅助 14/12。
- **触控**：≥44px；错误有文字/图标，不能只靠颜色。
- **布局**：移动 390×844 主稿，360/768 检查；管理 1440×900。

### 7.2 Figma 变量

- 复制 SDS Community 文件，**不要直接 Save Library**；Library 变量只读。
- 先改 `brand` primitive ramp，再改 semantic；不要逐个按钮/卡片改 Fill。
- 变量映射与导入步骤见 [React_SDS_操作指南.md](React_SDS_操作指南.md)。
- 免费版在 SDS 副本内设计；发布跨文件 Library / 多 Mode 需付费或 Education。

### 7.3 代码 tokens

- React 侧：`docs/lab2/tokens/react-sds/`
  - `sds-theme.css`：CSS Variables
  - `tailwind.config.js` / `tailwind-theme.css`：Tailwind 3/4
  - `react-sds.tokens-studio.json` / `react-sds.dtcg.json`：Figma 变量导入
- 旧 Vue/Element Plus tokens 已删除，不再保留两套真相。

## 9. 数据层

```text
FastAPI /openapi.json
  → openapi-typescript → src/api/schema.d.ts
  → openapi-fetch client（cookie/CSRF/错误归一化）
  → TanStack Query hooks（queryKey 含 ledgerId/status/page）
  → 页面
```

- `queryKey` 必须包含 `ledgerId`、筛选、分页；审核/还款后失效 `reviews`、`ledger`、`transactions`、`settlement`。
- 幂等键由前端生成（UUID），同一次提交重试复用同一个 key；服务端仍做幂等。
- 错误统一映射 `AppError`：网络、401、403、409、422、5xx；表单错误落到字段，业务错误落到 Toast/Alert。
- 金额、日期、状态文案在 `lib` 统一格式化，页面不重复写。

## 15. 实现细节补充（2026-10-26）

### 15.1 数据模型与关键约束

| 表 | 关键字段 | 约束/说明 |
| --- | --- | --- |
| `users` | id、account、password_hash、status、must_change_pwd、contact | 账号由维护端开通；不开放注册；密码只存哈希 |
| `ledgers` | id、name、purpose、currency、status、created_by | currency 固定 CNY；status = 使用中 / 已归档 |
| `memberships` | id、ledger_id、user_id、status、join_seq、joined_at、left_at | `unique(ledger_id, user_id)`；退出保留历史，不物理删除；join_seq 用于分摊尾差 |
| `membership_roles` | membership_id、role、granted_by、granted_at、revoked_at | `unique(membership_id, role) WHERE revoked_at IS NULL`；ADMIN 与 REVIEWER 可并存；管理员不自动获得审核权 |
| `membership_periods` | id、membership_id、joined_at、left_at | 每次加入/退出一段；重入保留 join_seq 与历史，不覆盖旧区间 |
| `invitations` | id、ledger_id、token_hash、expires_at、used_at、revoked_at、created_by | 只存 token 哈希；一次性、7 天有效；使用后写 used_at |
| `categories` | id、ledger_id、type、name、status | 账本内唯一；停用后旧账保留、新账不可选 |
| `transactions` | id、ledger_id、type、current_version_id、created_by | 业务身份；只指向当前生效版本 |
| `transaction_versions` | id、transaction_id、ledger_id、version_no、status、voided_from_status、entered_by_membership_id、amount_cents、occurred_on、category_id、payer_membership_id、note、submitted_at、approved_at、reviewed_by | `unique(transaction_id, version_no)`；金额整数分；status 含 SUPERSEDED；approved_at 用于退出成员历史范围 |
| `allocations` | id、version_id、membership_id、kind、amount | 分摊/受益；同一版本同一成员唯一；合计必须等于版本金额 |
| `change_requests` | id、transaction_id、type、status、attempt_no、reason、base_version_id、proposed_payload、applicant_membership_id、handler_membership_id | 同一 transaction 最多一个 `status=PENDING`；部分唯一索引；重提保留 attempt_no 与历次记录 |
| `budgets` | id、ledger_id、month、amount、updated_by | `unique(ledger_id, month)`；month 用北京时间自然月 |
| `repayments` | id、ledger_id、from_membership_id、to_membership_id、amount、status、created_by、confirmed_by、confirmed_at | 方向、双方成员、金额 > 0；状态 = 待确认/已确认/已拒绝/已撤销 |
| `repayment_corrections` | id、repayment_id、status、attempt_no、correct_amount_cents、reason、applicant_membership_id、handler_membership_id、replacement_repayment_id | 同一 repayment 最多一个处理中申请；原付款人申请、原收款人处理；正确额为 0 时 replacement 为空 |
| `audit_logs` | id、ledger_id（可空）、actor_user_id、actor_membership_id（可空）、action、object_type、object_id、before_json、after_json、reason、trace_id、created_at | 只追加；与业务变更同事务写入；账号维护日志 ledger_id 为空，单独授权查询 |
| `idempotency_keys` | key、actor_user_id、scope、request_hash、response_json、created_at、expires_at | `unique(key, actor_user_id, scope)`；同 key 同 body 返回原结果；不同 body 409；定期清理过期记录 |

**金额与时间：** 推荐整数分 `amount_cents BIGINT`（备选 `numeric(12,2)` + Python `Decimal`），不用 float；业务日期按北京时间，存储统一 UTC，预算月份按发生日期归属。分配尾差按 `memberships.join_seq` 升序补分。

### 15.2 核心事务边界

**统一锁顺序（所有影响余额/额度/状态的写操作）：**

`BEGIN → pg_advisory_xact_lock(actor,scope,key) → 幂等判定 → SELECT ledgers ... FOR UPDATE → 重查权限/账本状态/版本/额度 → 业务写入 → 审计 + 幂等 → COMMIT`

- 锁前鉴权只做快速拒绝，**取得账本行锁后必须重查**成员身份、角色、账本状态、记录状态、版本号、还款额度。
- 顺序固定为 `ledgers → transactions → transaction_versions → repayments`，避免审核、还款、角色撤销、归档之间死锁。
- 2 个 Uvicorn worker 共享 PostgreSQL 行锁与幂等表，不使用进程内锁。

**审核通过（最关键）：**

1. 快速校验会话/成员/审核角色；只做明显拒绝，**不在锁前直接回放幂等**。
2. `BEGIN`；先取同键事务级 advisory lock，再查幂等：已完成且同 body 则 `ROLLBACK` 返回原结果；同键不同 body 返回 409；首次则继续。
3. 锁账本 → transaction → version；**锁后重查**成员仍 ACTIVE、审核角色仍在、账本仍 ACTIVE、记录仍为 `待审核`、版本号一致、审核人不是录入人/申请人。
4. 更新版本为 `已审核`；首次通过设置 `transactions.current_version_id`。
5. 仅当类型为支出时，按 `occurred_on` 所在月重算预算；收入不占预算。重算全账本成员净余额。
6. 以**变更后的固定余额快照**读取全部待确认还款并 `FOR UPDATE`，一次性合并计算所有超限/方向失效，撤销全部相关记录（REQ-026）；不边撤边缩小范围。
7. 同事务写审计日志（含自动撤销明细）、写幂等结果，再 `COMMIT`；返回最新统计/预算/余额。
8. 任一步失败整体回滚；状态/版本冲突返回 409，客户端刷新后再试。

**更正/作废通过：**

- 两条路径都先锁账本，校验 `base_version_id`/当前版本；处理人必须是合格审核员，且**不是申请人、不是版本录入人**。
- 更正：生成新版本 → 旧版本 `SUPERSEDED` → `current_version_id` 迁移到新版本 → 重算；只让新版本计一次。
- 作废：原版本 `VOID` → **`current_version_id = NULL`** → 退出计算；历史版本和审计保留，不删除。

**还款确认：** 同样先锁账本行，再锁相关 membership/repayment；排除本笔自身占用后重查额度，更新状态与余额，调用 `afterBalanceChange`（固定快照/一次撤销）并同事务审计；重复确认返回原结果。

**还款纠错：** 原付款人申请、原收款人处理；处理中原还款仍有效；同意时撤销原还款，正确额 > 0 才生成正确金额的已确认还款，二者同事务；随后调用 `afterBalanceChange`；不重新占用建议额度。

### 18.2 版本与申请生命周期

- `transaction_versions.status` 增加 `SUPERSEDED`；只有 `APPROVED + current_version_id + 非 VOID` 参与统计/预算/余额。
- 首次审核通过时设置 `transactions.current_version_id`；更正通过时生成新版本、旧版本 `SUPERSEDED`、指针迁移；作废时版本 `VOID` 且 **`current_version_id = NULL`**。
- `Approved` 不是终态：可因更正进入 `SUPERSEDED`，或因作废进入 `VOID`；已作废/已失效才是终态。
- `change_requests` 增加 `attempt_no`；同一 transaction 最多一个 `PENDING`；驳回/撤回的实例终结，重提创建新 attempt（attempt_no+1），不覆盖旧记录。
- `repayment_corrections` 独立于更正/作废：原付款人申请、原收款人处理；处理中不影响余额；同意时撤销原还款，正确额 > 0 才生成正确金额的已确认还款，二者同事务；正确额 = 0 不新建；驳回/撤回后重提同样新建 attempt。
- 所有申请处理都校验 `base_version_id`/当前版本和处理人独立性。

### 18.3 幂等、锁与审计

- 统一锁顺序（所有写入口）：`advisory(actor,scope,key) → ledgers → transactions → transaction_versions → repayments`；先幂等判定，再锁账本；锁后重查权限、状态、版本、额度。不得在锁前直接回放幂等结果。
- 审核、更正/作废、还款确认、还款纠错、角色撤销、归档使用同一顺序；2 个 worker 共享数据库锁与幂等表，不使用进程内锁。
- 抽取 `afterBalanceChange(ledgerId, snapshot)`：审核通过、更正/作废通过、还款确认、还款纠错同意都必须在同一事务调用它；它负责固定变更后余额快照、全量读取待确认、合并失效方向、一次撤销全部、写关联审计。REQ-026 不只覆盖审核。
- `idempotency_keys` 唯一键 `(key, actor_user_id, scope)`；与业务结果**同一事务**写入；同 key 同 body 返回原结果，不同 body 409；过期记录定期清理。
- 同键并发：`BEGIN → pg_advisory_xact_lock(hashtext(actor || ':' || scope || ':' || key)) → SELECT idempotency`；拿到锁后再判断“已完成/首次”，同键请求串行化，避免先查后写竞态；完成时 upsert response 后 `COMMIT`，崩溃回滚释放锁，不留下“处理中”脏行。
- `audit_logs.ledger_id` 可空；账号开通/重置日志无账本，仅维护端可查；业务日志按原业务可见范围和 actor 历史范围过滤。
- 审计日志、自动撤销明细、幂等结果与业务变更同事务提交；失败整体回滚。

### 18.4 退出、重入与历史范围

- `membership_periods` 记录每次加入/退出的区间；`join_seq` 在成员首次加入时固定，重入不改变。
- 历史可见范围：`transaction_versions.approved_at < membership.left_at` 的版本，以及这些版本引用的更正/日志；退出后补录的早日期新账不可见。
- 重新加入：保留原 membership、历史记录和首次加入顺序；默认普通成员，原管理员/审核员权限不自动恢复，需重新授予。
- 归档检查覆盖“因历史更正产生往来的退出成员”；退出成员在历史往来中可登记/确认本人还款、发起/处理本人还款纠错。
- 未生效作废账沿用原可见范围；范围由 `transactions.created_by + void 前状态 + actor 历史角色` 推导，不额外存快照；曾生效的作废账对在册成员可见。
- `approved_at` 只写首次生效时间，后续审核/更正不得覆盖；新版本有自己的 `approved_at`。
- 版本录入人 `entered_by_membership_id`：首版 = 交易创建者；更正版 = 更正申请人；写入后不可变；审核/处理人不得等于该成员。

### 18.5 性能与索引

在 100 用户、单账本 20 成员/5,000 支出/1,000 收入、全系统 20,000 支出/4,000 收入的目标下，先保证查询路径有索引；不引入缓存/读写分离。

| 索引 | 用途 |
| --- | --- |
| `transaction_versions(ledger_id, occurred_on DESC, created_at DESC)` | 账目列表、日期倒序分页 |
| `transaction_versions(transaction_id, status)` | 详情、当前版本、审核校验 |
| `change_requests(transaction_id) WHERE status='PENDING'` | 一记录一待处理申请 |
| `repayments(ledger_id, status)` | 待确认/余额相关读取 |
| `budgets(ledger_id, month)` UNIQUE | 同月唯一预算 |
| `audit_logs(ledger_id, created_at DESC)` | 日志查询 |
| `membership_roles(membership_id, role) WHERE revoked_at IS NULL` UNIQUE | 仅有效授权唯一；历史撤权行保留 |
| `idempotency_keys(key, actor_user_id, scope)` UNIQUE | 幂等 |

- 列表固定每页 20 条，先按条件过滤再 join 分配，避免 N+1；统计用聚合 SQL，不把全量记录拉到应用层。
- 验收时用 `EXPLAIN (ANALYZE, BUFFERS)` 记录执行计划；2 秒目标按 REQ-031 的 100 次/95 次口径测，不把规模当硬上限。

### 18.6 留存、备份与验收追踪

- 备份：每日 `pg_dump`，成功间隔 ≤24h，保留最近 7 次成功备份，主数据与备份介质分离；失败记录并通知乙方，不能静默跳过。
